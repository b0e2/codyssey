## 2. Git과 GitHub

### 2.1 Git

Git은 파일의 변경 이력을 관리하는 분산 버전 관리 시스템이다. 어떤 파일을 누가, 언제, 왜 변경했는지 커밋 단위로 기록할 수 있다. 이전 상태를 확인하거나 여러 사람의 변경 사항을 합치는 기능도 제공한다.

Git의 주요 목적은 다음과 같다.

- 파일 변경 이력 관리
- 이전 버전 확인 및 복구
- 브랜치를 이용한 독립적인 작업
- 여러 작업자의 변경 내용 병합

### 2.2 GitHub

GitHub는 Git 저장소를 원격에서 관리하고 공유할 수 있는 협업 플랫폼이다. Git의 버전 관리 기능에 Issue, Pull Request, Code Review, Branch Protection 등의 협업 기능을 제공한다.

| 구분 | Git | GitHub |
|---|---|---|
| 역할 | 파일과 변경 이력 관리 | 원격 저장소와 협업 관리 |
| 동작 위치 | 주로 로컬 컴퓨터 | 원격 서버와 웹사이트 |
| 주요 기능 | add, commit, branch, merge | Issue, PR, Review, 권한 관리 |

Git으로 로컬 변경 이력을 만들고, GitHub를 통해 그 변경 이력을 팀원과 공유한다고 이해할 수 있다.

## 3. Git의 세 가지 작업 영역

Git은 파일 변경을 다음 세 영역으로 관리한다.

1. **Working Directory**: 실제로 파일을 작성하고 수정하는 공간
2. **Staging Area**: 다음 커밋에 포함할 변경 사항을 선택해 두는 공간
3. **Repository**: 커밋된 변경 이력이 저장되는 공간

```text
파일 수정
   ↓ git add
Staging Area
   ↓ git commit
Local Repository
   ↓ git push
Remote Repository
```

`git add`는 파일을 Git에 영구 저장하는 명령이 아니라, 다음 커밋에 포함할 변경을 선택하는 명령이다. `git commit`을 실행해야 로컬 저장소에 하나의 변경 이력으로 기록되며, `git push`를 해야 원격 GitHub 저장소에 공유된다.

## 4. GitHub Flow

GitHub Flow는 `main` 브랜치를 중심으로 기능별 브랜치를 만들고 Pull Request를 통해 병합하는 협업 방식이다.

```text
Issue 생성
   ↓
최신 main 확인
   ↓
feature 브랜치 생성
   ↓
작업 및 Commit
   ↓
원격 브랜치로 Push
   ↓
Pull Request 생성
   ↓
Code Review 및 수정
   ↓
Approve
   ↓
main에 Merge
   ↓
Issue 종료
```

### GitHub Flow를 사용하는 이유

- 팀원별 작업을 서로 다른 브랜치로 분리할 수 있다.
- 완성되지 않은 코드가 바로 `main`에 들어가는 것을 방지할 수 있다.
- PR에서 변경 이유와 구현 내용을 설명할 수 있다.
- 병합 전에 다른 팀원의 검토를 받을 수 있다.
- 문제 발생 시 변경 과정과 의사결정 기록을 추적할 수 있다.

`main`은 팀의 기준이 되는 브랜치이므로 항상 실행 가능한 상태를 유지해야 한다. 따라서 코드뿐 아니라 문서 수정도 feature 브랜치에서 진행한 뒤 PR을 통해 병합한다.

## 5. Issue

Issue는 해야 할 작업, 버그, 개선 사항 등을 등록하고 추적하는 단위이다. 작업을 시작하기 전에 Issue를 만들면 무엇을 왜 해야 하는지 팀원과 공유할 수 있다.

### Issue에 포함할 내용

- 작업 제목
- 작업 내용
- 완료 조건
- 담당자(Assignee)
- 작업 분류(Label)
- 필요한 참고 사항

### 완료 조건이 중요한 이유

“기능 구현”처럼 범위가 모호하면 작업자와 리뷰어의 완료 기준이 달라질 수 있다. 반면 다음과 같이 완료 조건을 작성하면 PR을 검토할 기준이 생긴다.

```markdown
## 완료 조건

- [ ] 문자열을 뒤집어 반환하는 함수를 구현한다.
- [ ] 빈 문자열 입력을 확인한다.
- [ ] 함수 사용 예시를 작성한다.
```

PR 본문에 `Closes #3`과 같이 작성하면 해당 PR이 병합될 때 연결된 Issue를 자동으로 종료할 수 있다.

## 6. Branch

브랜치는 기존 코드에 영향을 주지 않고 독립적으로 작업하기 위한 분기점이다. 팀원마다 별도의 feature 브랜치를 사용하면 동시에 작업하더라도 서로의 미완성 변경이 섞이지 않는다.

### 브랜치 생성 전 최신 main을 받는 이유

오래된 `main`에서 브랜치를 만들면 이미 병합된 다른 팀원의 변경을 포함하지 못한다. 이후 PR을 병합할 때 충돌 가능성이 커지므로 브랜치 생성 전 원격 `main`을 최신 상태로 맞춘다.

```bash
git switch main
git pull --ff-only origin main
git switch -c feature/<name>-<topic>
```

### 브랜치 이름 규칙

```text
feature/<name>-<topic>
```

예시:

```text
feature/taedong-string-utils
feature/minsu-contributing-guide
```

브랜치 이름만 보고 작업자와 작업 내용을 파악할 수 있도록 작성한다.

## 7. Commit

커밋은 하나의 의미 있는 변경 단위를 저장한 기록이다. 좋은 커밋은 나중에 변경 이유를 파악하고 특정 변경만 되돌리기 쉽게 만든다.

### 커밋 메시지 형식

```text
<type>: <subject>
```

| Type | 의미 |
|---|---|
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서 추가 또는 수정 |
| `refactor` | 동작 변경 없이 코드 구조 개선 |
| `test` | 테스트 추가 또는 수정 |
| `chore` | 설정이나 기타 유지보수 작업 |

좋은 예시:

```text
feat: add string reverse utility
fix: handle empty string input
docs: document pull request rules
```

피해야 할 예시:

```text
update
final
temp
fix
```

커밋은 가능한 한 하나의 목적만 담는다. 기능 구현, 문서 수정, 불필요한 파일 추가가 한 커밋에 섞이면 리뷰와 문제 추적이 어려워진다.

## 8. Push, Pull Request, Merge의 차이

세 용어는 서로 다른 작업을 의미한다.

| 용어 | 의미 |
|---|---|
| Push | 로컬 커밋을 원격의 같은 브랜치에 전송 |
| Pull Request | 내 브랜치의 변경을 대상 브랜치에 병합해 달라고 요청 |
| Merge | 두 브랜치의 변경 이력을 실제로 합침 |

feature 브랜치에 `push`했다고 해서 `main`이 변경되는 것은 아니다. PR을 생성하고 리뷰와 승인을 받은 뒤 `merge`해야 feature 브랜치의 변경이 `main`에 포함된다.

### GitHub PR 병합 방식

GitHub는 PR을 `main`에 병합할 때 세 가지 방식을 제공하며, 방식에 따라 
feature 브랜치의 커밋 이력이 main에 남는 형태가 달라진다.

| 방식 | main에 남는 형태 |
|---|---|
| Merge commit | feature 브랜치의 커밋이 모두 유지되고, 병합 지점에 별도의 merge 커밋이 추가된다. |
| Squash and merge | feature 브랜치의 모든 커밋이 하나의 커밋으로 합쳐져 main에 기록된다. |
| Rebase and merge | 각 커밋은 유지되지만 main 위에 재배치되어 병합 커밋 없이 이어 붙는다. |

저장소 설정(Branch Protection 또는 Settings)에서 특정 방식만 허용하도록 
제한할 수 있다. 예를 들어 Squash and merge만 허용된 저장소에서는 
7장에서 강조한 "목적별로 나눈 커밋"이 main에는 하나로 합쳐져 보인다는 점을 
미리 알고 있어야 혼란이 없다.

## 9. Pull Request

Pull Request는 작업 브랜치의 변경 사항을 `main`에 병합하기 전에 팀원에게 설명하고 검토를 요청하는 공간이다.

### PR 본문에 포함할 내용

```markdown
## 연결 이슈

- Closes #3

## 변경 사항 (What)

- 무엇을 변경했는지 작성한다.

## 변경 이유 (Why)

- 해당 변경이 왜 필요한지 작성한다.

## 테스트/검증 방법 (How)

- 어떤 입력과 방법으로 확인했는지 작성한다.
```

PR은 단순히 코드를 합치기 위한 버튼이 아니다. 변경 내용과 결정 이유, 리뷰 의견, 수정 과정이 한곳에 남는 협업 기록이다.

## 10. Code Review

코드 리뷰는 다른 팀원의 변경 내용을 확인하고 질문이나 개선 의견을 나누는 과정이다. 오류를 찾는 것뿐 아니라 구현 의도를 공유하고 코드의 가독성, 안정성, 유지보수성을 높이는 목적이 있다.

### 실질적인 리뷰 예시

- 빈 문자열이나 `0` 같은 경계 입력에서도 정상 동작하는지 질문한다.
- 함수명이나 변수명이 역할을 충분히 설명하는지 확인한다.
- 중복 코드나 복잡한 조건문을 단순화할 방법을 제안한다.
- Issue의 완료 조건이 모두 충족됐는지 확인한다.
- 문서의 설명과 실제 코드 동작이 일치하는지 확인한다.

```text
빈 문자열이 입력될 때도 현재 함수가 정상적으로 동작하는지 확인하면 좋겠습니다.
```

`LGTM`, `좋아요`, `확인했습니다`만 남기면 어떤 부분을 검토했는지 알기 어렵다. 이러한 표현을 사용하더라도 구체적인 검토 의견을 함께 작성해야 한다.

### 리뷰 작성자의 책임

1. 리뷰 의견의 의미를 확인한다.
2. 필요한 경우 같은 PR 브랜치에서 코드를 수정한다.
3. 수정 내용을 별도 커밋으로 push한다.
4. 리뷰 댓글에 무엇을 반영했는지 답변한다.
5. 반영하지 않는다면 그 이유를 설명한다.

공유된 PR의 기존 커밋을 `amend`하여 바꾸기보다는 새로운 수정 커밋을 추가하는 것이 변경 과정을 확인하기 쉽다.

## 11. Branch Protection과 권한

Branch Protection은 `main`과 같은 중요한 브랜치에 정해진 절차 없이 변경 사항이 들어오는 것을 막는 기능이다.

이번 협업에서 필요한 핵심 규칙은 다음과 같다.

- `main`에 병합하기 전에 PR을 요구한다.
- 다른 팀원 최소 1명의 승인을 요구한다.
- 해결되지 않은 리뷰 대화가 있다면 병합하지 않는다.
- 관리자도 규칙을 따르게 하려면 우회 방지 설정을 적용한다.

저장소 권한이 `Write`인 팀원은 feature 브랜치를 push하고 PR을 생성할 수 있다. 그러나 보호된 `main`에는 직접 push하지 못하며, PR과 승인을 통해 변경해야 한다. 저장소 관리자는 설정 관리를 위해 `Admin` 권한을 유지할 수 있다.

## 12. Merge Conflict

충돌은 Git이 두 변경 사항을 자동으로 합칠 수 없을 때 발생한다. 대표적으로 두 팀원이 같은 파일의 같은 줄을 서로 다르게 수정했을 때 발생한다.

### 충돌 마커

```text
<<<<<<< HEAD
현재 브랜치의 내용
=======
병합하려는 브랜치의 내용
>>>>>>> origin/main
```

- `<<<<<<< HEAD`: 현재 브랜치의 내용
- `=======`: 두 변경 사항의 구분선
- `>>>>>>> origin/main`: 병합하려는 브랜치의 내용

충돌 해결은 단순히 마커를 삭제하는 작업이 아니다. 어떤 변경을 유지할지 관련 팀원과 합의한 뒤 최종 내용을 직접 작성해야 한다.

### 충돌 해결 순서

1. `git status`로 충돌 파일을 확인한다.
2. 충돌 마커와 양쪽 변경 내용을 확인한다.
3. 관련 팀원과 최종 결과를 협의한다.
4. 최종 내용으로 파일을 수정하고 충돌 마커를 제거한다.
5. 프로그램 또는 문서가 정상인지 검증한다.
6. 해결한 파일을 stage하고 커밋한다.
7. PR에 충돌 원인과 해결 방법을 기록한다.

```bash
git fetch origin
git merge origin/main
git status

# 충돌 파일 수정 후
git add <conflicted-file>
git commit -m "fix: resolve merge conflict"
git push
```

충돌 해결 과정에는 참여자, 충돌 브랜치와 파일, 원인, 협의 내용, 선택한 해결 방법, 검증 결과, 관련 PR과 커밋을 기록한다.

## 13. Git 트러블슈팅 명령어

비슷해 보이는 명령어라도 변경 이력에 미치는 영향이 다르다. 특히 원격에 공유했는지를 기준으로 안전한 명령을 선택해야 한다.

### 13.1 `git commit --amend`

가장 최근 커밋의 메시지나 내용을 수정할 때 사용한다.

```bash
git commit --amend -m "docs: correct commit message"
```

amend를 실행하면 기존 커밋을 직접 수정하는 것이 아니라 새로운 커밋 해시를 가진 커밋으로 교체된다. 따라서 아직 원격에 공유하지 않은 자신의 최근 커밋에 사용하는 것이 안전하다.

### 13.2 `git reset --soft HEAD~1`

가장 최근 커밋을 취소하되 변경 사항을 Staging Area에 유지할 때 사용한다.

```bash
git reset --soft HEAD~1
git status
git diff --cached
```

커밋에 파일을 잘못 묶었거나 커밋을 다시 구성하고 싶을 때 사용할 수 있다. 커밋 이력을 변경하므로 원격에 공유하지 않은 자신의 커밋에 사용한다.

### 13.3 `git revert <commit-hash>`

특정 커밋의 변경을 반대로 적용하는 새로운 커밋을 생성한다.

```bash
git revert <commit-hash>
```

기존 커밋을 히스토리에서 삭제하지 않기 때문에 이미 원격 저장소에 공유된 커밋을 취소할 때 적합하다. 원래 커밋과 되돌림 커밋이 모두 기록으로 남는다.

### 13.4 `git stash`

아직 커밋하지 않은 변경 사항을 임시로 보관할 때 사용한다.

```bash
git stash push -m "save unfinished work"
git stash list
git switch <other-branch>

git switch <original-branch>
git stash pop
```

작업 도중 긴급하게 다른 브랜치로 이동해야 할 때 사용할 수 있다. 기본 stash는 추적 중인 파일의 변경을 대상으로 한다. 새로 생성한 미추적 파일도 함께 보관하려면 `git stash push -u`를 사용한다.

### 13.5 명령어 비교

| 명령어 | 목적 | 변경 사항 상태 | 적절한 사용 시점 |
|---|---|---|---|
| `commit --amend` | 최근 커밋 수정 | 새 커밋 해시로 교체 | push 전 |
| `reset --soft` | 최근 커밋 취소 | 변경 사항은 stage 상태 유지 | push 전 |
| `revert` | 특정 커밋의 변경 취소 | 취소 내용의 새 커밋 생성 | push 후에도 안전 |
| `stash` | 미완료 변경 임시 보관 | 커밋하지 않고 별도 보관 | 브랜치 이동 전 |

## 14. 안전한 Git 작업 습관

Git 명령어를 실행하기 전에 현재 브랜치와 변경 상태를 확인한다.

```bash
git status
git branch --show-current
git log --oneline -5
```

팀 협업에서는 다음 사항을 지킨다.

- `main`에 직접 작업하거나 직접 push하지 않는다.
- 다른 팀원의 브랜치를 임의로 수정하거나 삭제하지 않는다.
- 공유된 브랜치에서 `git push --force`를 사용하지 않는다.
- 충돌 내용을 이해하지 못한 상태에서 한쪽 변경을 삭제하지 않는다.
- `reset`과 `amend`는 원격에 공유하지 않은 자신의 커밋에 사용한다.
- 이미 공유된 변경을 취소할 때는 `revert`를 우선 고려한다.
- PR을 병합하기 전에 승인, 리뷰 대화, 충돌, 실행 결과를 확인한다.
