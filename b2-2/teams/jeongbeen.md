# 정빈

## 자기소개

안녕하세요. 마리너 2기 정빈입니다.

이번 프로젝트에서는 GitHub Flow를 기반으로 Issue, 브랜치, 커밋, Pull Request, 코드 리뷰가 연결되는 협업 과정을 연습하고 있습니다.  
팀원들과 작업 상황을 명확하게 공유하고, 리뷰 의견을 적극적으로 반영하며 함께 완성도 높은 결과물을 만드는 것을 목표로 하고 있습니다.

## 공부한 내용

### 브랜치와 GitHub Flow

Git 브랜치는 독립된 파일 복사본이 아니라 특정 커밋을 가리키는 포인터라는 점을 배웠습니다. 작업 단위별로 브랜치를 분리하면 `main` 브랜치를 안정적으로 유지하면서 여러 팀원이 각자의 작업을 독립적으로 진행할 수 있습니다.

GitHub Flow에서는 최신 `main`에서 feature 브랜치를 생성하고, 작업이 끝나면 Pull Request와 코드 리뷰를 거쳐 다시 `main`에 병합합니다. 이를 통해 `main`을 항상 정상적으로 동작하는 상태로 유지할 수 있습니다.

### Issue, Pull Request와 코드 리뷰

Issue는 작업 내용과 완료 조건을 기록하고, 팀의 진행 상황을 추적하는 데 사용합니다. 작업을 시작하기 전에 Issue를 생성하면 담당자와 작업 목적을 팀원들이 명확하게 확인할 수 있습니다.

Pull Request에는 `Closes #이슈번호`를 작성하여 관련 Issue를 연결합니다. 또한 What, Why, How를 작성하면 변경 내용과 이유, 검증 방법을 리뷰어에게 명확하게 전달할 수 있습니다.

코드 리뷰에서는 단순히 `LGTM`만 남기는 것이 아니라 특정 코드나 문서를 근거로 질문하거나 개선안을 제안해야 한다는 점을 배웠습니다. 작성자는 리뷰 의견에 답변하고 필요한 내용을 수정함으로써 변경 과정과 의사결정 기록을 남길 수 있습니다.

### 충돌과 Git 문제 해결

여러 브랜치에서 같은 파일의 같은 영역을 다르게 수정하면 Git이 변경 내용을 자동으로 합치지 못해 충돌이 발생할 수 있습니다.

충돌이 발생하면 `<<<<<<<`, `=======`, `>>>>>>>` 마커를 통해 각 브랜치의 변경 내용을 확인합니다. 이후 관련 팀원과 유지할 내용을 협의하고 충돌 마커를 제거한 뒤, 최종 결과가 정상적으로 동작하는지 검증해야 합니다.

Git 문제 상황에 따라 사용하는 명령도 다르다는 점을 공부했습니다.

- `git commit --amend`: 최근 커밋의 내용이나 메시지 수정
- `git reset --soft HEAD~1`: 로컬 커밋을 취소하면서 변경 내용 유지
- `git revert`: 원격에 공유된 커밋을 새로운 커밋으로 안전하게 되돌리기
- `git stash` / `git stash pop`: 완료되지 않은 작업을 임시로 보관하고, 필요한 시점에 다시 복원하기
